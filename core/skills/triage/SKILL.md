# Triage

This skill covers two distinct protocols. Match the user's request to the right one before doing anything.

| If the request is about... | Use section |
|---|---|
| GitHub/tracker issues or PRs — "#42", "ready-for-agent", "what needs my attention on the tracker" | Issue / PR Triage |
| The AOS capture inbox — "triage the inbox", "groom my ideas", "what should I work on next", weekly review, pre-release | AOS Inbox Grooming |

## Issue / PR Triage

Move issues on the project issue tracker through a small state machine of triage roles.

If this repo treats external pull requests as a request surface (see the issue-tracker config), triage covers them too: **a PR is an issue with attached code**, using the same roles, same states, and same machine, with a few deltas marked "for a PR" below. Resolve a bare `#42` to an issue or PR per the tracker config.

Every comment or issue posted to the issue tracker during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

### Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md): how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): how the `.out-of-scope/` knowledge base works

### Roles

Two **category** roles:

- `bug`: something is broken
- `enhancement`: new feature or improvement

Five **state** roles:

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on reporter for more information
- `ready-for-agent`: fully specified, ready for an AFK agent
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

For a PR, the same states read against the attached code: `ready-for-agent` means a brief is attached and an agent should take the next step on the diff; `ready-for-human` means it's ready for a human to merge.

Every triaged issue should carry exactly one category role and one state role. If state roles conflict, flag it and ask the maintainer before doing anything else.

These are canonical role names. The actual label strings used in the issue tracker may differ. The mapping should have been provided to you. If not, tell the user to run `/setup-matt-pocock-skills`.

State transitions: an unlabeled issue normally goes to `needs-triage` first; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time; flag transitions that look unusual and ask before proceeding.

### Invocation

The maintainer invokes `/triage` and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

### Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabeled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation.

When PRs are in scope, include external PRs in these buckets and tag each line `[PR]` or `[issue]`. Discovery surfaces only *external* PRs (the tracker config defines who counts as external), so a collaborator's in-flight PR is not triage work. This filter is discovery-only; an explicitly named PR is always triaged regardless of author.

Show counts and a one-line summary per item. Let the maintainer pick.

### Triage a specific issue or PR

1. **Gather context.** Read the full issue or PR (body, comments, labels, author, dates; for a PR, the diff too). Parse any prior triage notes so you don't re-ask resolved questions. Explore the codebase using the project's domain glossary, respecting ADRs in the area. Run two checks against the codebase: (a) **redundancy**: search for an existing implementation of the requested behavior by domain concept (not just the request's wording), and report where you looked. If found, it's an already-implemented `wontfix` (step 5). (b) **prior rejection**: read `.out-of-scope/*.md` and surface any that resembles this request.

2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a brief codebase summary relevant to the request (including whether it's already implemented). Wait for direction.

3. **Verify the claim.** Before any grilling, check that the claim holds up. For a bug, reproduce it from the reporter's steps. For a PR, confirm the diff does what it claims: check it out, run the relevant tests or commands. Report what happened: confirmed (with code path), failed, or insufficient detail (a strong `needs-info` signal). A confirmed verification makes a much stronger agent brief.

4. **Grill (if needed).** If the request needs fleshing out, call the Skill tool twice, for "grilling" and "domain-modeling", and grill it into shape a round of questions at a time, sharpening domain terms and updating `CONTEXT.md`/ADRs inline as decisions land.

5. **Apply the outcome:**
   - `ready-for-agent`: post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: same structure as an agent brief, but note why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - `needs-info`: post triage notes (template below).
   - For `wontfix`, close the issue, with the comment depending on *why*:
     - **Already implemented**: the change already exists in the codebase. Point to where it lives; do **not** write to `.out-of-scope/` (that KB is for *rejected* requests, not built ones).
     - **Rejected (bug)**: give a polite explanation, then close.
     - **Rejected (enhancement)**: write to `.out-of-scope/`, link to it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: apply the role. Optional comment if there's partial progress.

### Quick state override

If the maintainer says "move #42 to ready-for-agent", trust them and apply the role directly. Confirm what you're about to do (role changes, comment, close), then act. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want to write an agent brief.

### Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

### Resuming a previous session

If prior triage notes exist on the issue or PR, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.

## AOS Inbox Grooming

You turn a pile of raw captures into **a decision per item**, then act and **drain the
inbox to zero**. You are the opposite of a backlog: nothing accumulates, everything gets a
verdict. Three rules keep you from degenerating into the stale-backlog problem you exist to
solve:

1. **Bets, not backlogs.** Every pass drains to zero. KILL deletes (re-advocate later) — no
   graveyard of stale tickets.
2. **Decisions, not analysis.** Every item leaves with exactly one verdict (Now/Next/Later/Kill)
   + a one-line rationale. Deferred ≠ unprocessed.
3. **Freshness guard.** Never trust a spec that claims "done" — verify against reality before
   folding an item into it. A done-but-isn't spec is STALE; reopen it.

### Step 0 — Detect project config (this is a reusable template)

The logic below is universal; the targets are per-project. **Discover from the filesystem —
never hardcode.** Missing config → graceful skip, not failure.

| Config | Detect | Used in |
|---|---|---|
| Inbox | `~/vault/knowledge/triage/inbox.md` (global) | GATHER |
| Captures | `~/vault/knowledge/triage/captures/` | GATHER |
| Specs corpus | `docs/specs/*.md` (subsumption corpus) | SUBSUMPTION |
| Initiatives | `~/vault/knowledge/initiatives/*.md` (status in frontmatter) | SUBSUMPTION + CONTRADICTION |
| Decisions | `docs/decisions/`, `vault/knowledge/decisions/` | CONTRADICTION |
| Release gate | `script/release`, `script/gate`, `docs/appstore/release-checklist.md` | SHIP integration |
| Auditors | enumerate `~/.claude/agents/` for `*-auditor` / the `axiom:*` fleet | ROUTE |
| Dev loop | `script/snap` (screenshot), `script/device` | freshness verification |
| Task system | `python3 ~/aos/core/engine/work/cli.py`, project prefix (e.g. `dod#`) | ACT |
| Other inboxes | work-CLI inbox, floating `t#`, project `scratchpad/` | GATHER (full dedup surface) |
| Build constraint | "one build at a time" / WIP=1 (read AGENTS.md) | EXECUTE/SHIP |

If no specs dir → skip subsumption. If no auditors → route audit-shaped items to a plain task
with the audit named in the description. If no `script/gate` → skip the ratchet check.

### The grooming algorithm (run to ZERO)

```
1. GATHER         All raw items: inbox.md + captures/ + work-CLI inbox + floating t# +
                  relevant scratchpad/. One pile, one pass. (Do NOT pull expanded-note
                  bodies into context — read the inbox lines + capture titles; open a
                  capture note only when a verdict needs it.)
2. DEDUP          Collapse exact + near-duplicates. Keep richest phrasing; remember reach
                  (how many times reported) — it raises priority, it isn't lost.
3. CLUSTER        Group related items into themes. A cluster may become one spec or one bet.
4. CLASSIFY       Per item: TYPE + CLASS OF SERVICE + iOS SEVERITY SIGNALS (tables below).
5. CONTRADICTION  Cross-check items vs each other AND vs locked decisions/initiatives.
                  Surface conflicts ("X wants dark default, Y wants light") — never queue both silently.
6. SUBSUMPTION    Already covered by a FRESH spec or active initiative? → fold/annotate, no new work.
   (+FRESHNESS     Covered by a spec that claims "done"? → FRESHNESS GUARD: verify against reality
    GUARD)         (grep the code, `script/snap` the screen, check git) before trusting it.
                   Mismatch → spec is STALE → reopen; the item is evidence it's not done.
                   Not covered → genuinely new.
7. PRIORITIZE     Apply the rubric (below): appetite + class-of-service + cost-of-delay,
                  WSJF (CoD ÷ JobSize) as tie-break. A shortlist, not a ranked megalist.
8. DECIDE         One verdict per item: NOW · NEXT · LATER · KILL. Shape Up's 5 questions gate
                  NOW (problem real? appetite realistic? solution clear? timing right? capacity free?).
9. ACT            Route per the decision tree (below): direct task / spec / auditor / release-gate / kill.
10. DRAIN         Move every processed item out of inbox.md → archive/ (with its verdict + reason).
                  Inbox returns to ZERO.
```

### Classification

**Type:** `bug · feature · refactor · polish · content · chore · spike`

**Class of service** (drives interruption):
| Class | Trigger | Rule |
|---|---|---|
| **Expedite** | crash · data-loss · privacy/security leak · store-takedown risk | **Cap = 1.** Jumps the queue, may break WIP. |
| **Fixed-date** | Hijri/Ramadan tie-in · Apple deadline · submission slot | Schedule backward from the date. |
| **Standard** | normal features/bugs | FIFO within priority; respects WIP=1 build. |
| **Intangible** | refactor · tests · tech-debt · deprecation | Needs reserved capacity (a % per cycle) or it never happens. |

**iOS severity signals → tier → route:**
| Signal | Tier | Route to |
|---|---|---|
| crash | S1 | direct task NOW + `axiom:crash-analyzer` on the log |
| data-loss / migration risk | S1 | `axiom:swiftdata`/`core-data`/`database-schema-auditor` |
| App-Store-rejection / privacy-manifest | S1–S2 | `axiom:security-privacy-scanner` + `axiom:*shipping*` — **blocks release** |
| deprecation | S2 | task; becomes fixed-date when Apple sets a cutoff |
| a11y (VoiceOver/Dynamic Type/contrast/44pt) | S2 | `axiom:accessibility-auditor` — release-gate item |
| perf / jank | S2–S3 | `axiom:swiftui-performance-analyzer` / `performance-profiler` |
| energy / battery | S3 | `axiom:energy-auditor` |
| polish / content / copy | S3–S4 | rides along; never blocks |

### Prioritize → decide

`priority ≈ (severity × class-of-service weight × reach) ÷ appetite`. Then gate with judgment:

| Verdict | Rule |
|---|---|
| **NOW** | Expedite/S1, OR fixed-date due this cycle, OR high CoD ÷ small appetite — **and** passes all 5 Shape Up questions **and** WIP has room. This cycle. |
| **NEXT** | Real and shaped, lost the appetite/CoD contest. Eligible next window. One-line rationale. |
| **LATER** | Valid but low CoD / large appetite / unclear shaping. Park with a trigger ("revisit if N users hit it" / "after iOS 27 SDK"). |
| **KILL** | Duplicate · subsumed by a fresh spec · contradicts a locked decision · already done · "problem doesn't matter." **Delete** (re-advocate later). The anti-stale valve. |

WSJF tie-break for the last NOW slot: higher `CoD ÷ JobSize` wins.

### The digest (decisions, not analysis)

Write `~/vault/knowledge/triage/digests/YYYY-Www.md` and present it. Keep NOW to **3–5 bets.**

```markdown
# Triage digest — YYYY-Www

## NOW (this cycle)
- <title> · [type/project] · why · → <route: dod# task / auditor / spec>

## NEXT
- <title> · why it waits

## LATER
- <title> · park trigger

## KILL
- <title> · reason (done / dup / subsumed / doesn't matter)

Drained: N items → archive/
```

### ACT — routing decision tree

```
item →
  expedite / S1 crash|data-loss?         → direct task NOW + flag build-blocker (+ auditor on the artifact)
  a domain auditor matches the signal?   → dispatch that auditor (table above)
  cluster / design-shaped change?        → create or update a spec in docs/specs/
  covered by a FRESH spec/initiative?    → fold in / annotate; no new work
  covered by a STALE "done" spec?        → reopen the spec (freshness guard); item = evidence
  clear small next action?               → direct task (project prefix)
  fixed-date / blocker?                  → tag to the next release gate
  doesn't matter / dup / done?           → KILL
```

**Mechanics:**
- Promote NOW → `python3 ~/aos/core/engine/work/cli.py add "<title>" --project <p> --priority <N> --source-ref <spec-or-initiative>`
- Fold → `Edit` the spec/initiative (append the item + date).
- Reopen stale spec → flip its status / add a "REOPENED <date>: still not done — <evidence>" note.
- Resolved contradiction → write a short decision to `docs/decisions/<date>-<slug>.md`.
- Drain → append each processed line to `~/vault/knowledge/triage/archive/YYYY-Www.md` with `· <VERDICT>: <reason>`, then remove it from `inbox.md`'s `## Queue`. **Inbox ends at zero.**

### Release-gate integration (when triggered before a release)

Split the cycle's items into **block** vs **ride-along**:
- **BLOCK** the release: S1 (crash, data-loss), missing/wrong privacy manifest, App-Store-rejection
  risk, a11y regressions on core flows, or any `script/gate` metric that increased vs baseline.
- **RIDE ALONG** (never block): polish, copy/content, minor a11y nits, non-regression perf/energy
  wins, already-merged intangible refactors.
Fire the pre-submission auditors (accessibility, security-privacy, performance, energy) at triage
time so nothing is a surprise at the gate.

### Anti-pattern guards (hold these)

- Inbox only grows → **drain to zero every pass; KILL deletes.**
- Re-discussing items each pass → **one verdict per item.**
- Stale "done" specs → **freshness guard before folding.**
- Everything in-flight, nothing ships → **WIP=1 build; expedite cap=1.**
- Severity treated as priority → **priority = severity × CoS × reach ÷ appetite.**
- a11y/privacy found at submission → **route to auditors at triage; gates fire before release.**
- Runaway "almost done" → **appetite + circuit breaker: doesn't ship in its window → reshape/kill.**
- Refactors never happen → **reserved capacity for the intangible class.**

### Hard rules

- Output a **digest of decisions**, never a wall of analysis.
- **Drain to zero.** If an item can't get a verdict, that's a signal it needs shaping — say so, don't silently leave it.
- **Never auto-promote/kill without operator approval** of the digest. Present → approve → act.
- **Freshness guard is non-negotiable** before trusting any "done" spec.
- Keep the capture/triage boundary: capture writes raw; you do ALL routing, dedup, and judgment.
