## What the operator does to enable a second lane

```
1. aos claude-profile add cld2
2. cld2                          # once — then /login with the second account
3. aos claude-profile status     # confirms both `default` and `cld2` show "logged in"
```

That's the whole feature for interactive use — a second command that's a
second, isolated Claude Code session, sharing every part of the AOS layer
(skills, agents, rules, hooks, commands, projects, plugins, `CLAUDE.md`,
`settings.json`, `statusline.sh`, `keybindings.json`) except the login itself.

To also make headless spawns fail over to it — the bridge, Sentinel, the
memory-curate cron — create (or hand-edit) `~/.aos/config/claude-lanes.yaml`:

```yaml
lanes: [default, cld2]
```

This file is entirely the operator's: nothing in this release creates it.
Once it exists, `aos claude-profile add <name>` appends any *new* profile to
its `lanes:` list automatically and says so; a lane not yet in the list is
simply never tried. Order is priority order — `default` first means the
operator's own login is always tried first, and `cld2` only takes over once
`default` reports a usage-limit hit for that lane.

## What to verify after install

- `aos claude-profile list` shows `default` (unaffected — this release adds
  to `~/.claude`, never modifies it) and any profile the operator has added.
- `~/.local/bin/cld2` and `~/.local/bin/cld3` exist (migration 135) and print
  the one-line fix (`claude-profile add cld2`) rather than a stack trace, if
  the operator hasn't added that profile yet.
- Plain `cld` behaves exactly as before — no `CLAUDE_CONFIG_DIR` in its
  environment, same `--agent` flag, same everything. This is the one
  regression this release cannot afford: verify with `env | grep
  CLAUDE_CONFIG_DIR` inside a `cld` session (nothing) versus a `cld2` session
  (the profile's own config dir).
- No Keychain item was created or touched by `aos claude-profile add` —
  `security dump-keychain` (names only) before and after should be
  byte-identical modulo whatever the operator did by hand.
- If `~/.aos/config/claude-lanes.yaml` was added: trigger a real usage-limit
  message once (or just watch the logs the first time it happens) and confirm
  one `[lanes] ...` item lands in the work inbox (`work inbox` or `aos
  claude-profile status`'s `exhausted until` column), not a flood of them.

## Rollout

This Mini takes it on `edge`, same as every recent release. `faisal-mini`
takes the framework half unconditionally on its own update cycle — migration
135 puts `cld2`/`cld3` on his PATH too, since that's just plumbing — but gets
**no profiles**, because `claude-profile add` is never run by anything but the
operator. Until *his* operator runs `aos claude-profile add cld2` on that
machine and logs in, `cld2` there prints the one-line fix and exits 2, exactly
as designed: a launcher existing is not the same as an account being
configured, and this release does not confuse the two.
