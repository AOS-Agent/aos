# v0.7.7 — the system sheds what it never used

**Status: Ready to ship when the operator says so.** Everything below is built,
tested and dry-run. Nothing has been applied to any machine and the branch has
not been pushed or merged.

Branch: `release/0.7.7` · Base: `release/0.8.0` @ `2f7ea72` · VERSION: `v0.7.7`

---

## What this release does

A normal release of a system still under development. AOS keeps being developed
until Qren is ready; this release is not a freeze, not a farewell, and not a
switch to patches-only. It is a big cleanup: the system drops a service it
decommissioned, switches off arms that should never have been on by default,
clears years of junk out of the instance layer, and fixes the bug that was
generating that junk.

Fifteen migrations land, 108–122. They are separable — any one of them can be
held back without breaking the others.

### The decommission sweep (108–110)

Qareen is gone: the :4096 service, its 238-route API, the React screen, the
voice pipeline and the event bus. The work engine's ontology layer moved out of
it into `core/engine/work/ontology/`, so session and task linking now runs
in-process instead of POSTing to a service. Migration **108** boots out the three
LaunchAgents, kills stray deploy watchers, deletes the ~1.1 GB venv, drops the
dead ingest tables and removes the companion skill links; `qareen.db` itself
stays, because loop signals, cron telemetry, people intel and work sessions still
live in it. **109** retires four half-baked services — `companion`, `listen`,
`n8n`, `slack-watch` — removing their LaunchAgents, launchers and venvs (~2.2 GB).
**110** deregisters the `memory` MCP server, whose ChromaDB index had never
indexed a single document, and deletes its ~300 MB venv; QMD is the search layer.

### Four services become opt-in (111–112)

| Service | Why | Reversal |
|---|---|---|
| `work-runner` | `task_runs` held **zero rows on every machine audited** — 905 lines and a resident KeepAlive'd LaunchAgent that never once delegated a task | `work runner enable` |
| `sentinel` | Reads iMessage, drafts follow-through. Autonomous comms becomes a Qren arm | list under `enabled:`, reload plist |
| `converse` | Live multi-turn sessions. Same | same |
| `envoy` | Runs delegated outbound conversations with third parties. Same | same |

The mechanism is a new `enabled:` list in `~/.aos/config/services.yaml`
alongside the `disabled:` list reconcile already reads. **`enabled:` wins and is
never auto-disabled** — not by a migration, not by reconcile, not by anything.
Without that asymmetry, "off by default" and "off by decree" are the same code
path, and an operator who wants Sentinel gets it switched off under them on every
update.

`modules.yaml` had `work-runner` as `tier: core` while the service registry
called it `optional` — the precise drift the registry exists to prevent. Aligned.

### The instance gets cleaned (113–116)

- **368 test-fixture tasks** deleted from `work.db` (114). The test suite wrote
  to the real database for ~3.5 months; these are the six literal titles from
  `tests/test_engine.py`, 17% of the task table and the bulk of the `t#` bucket
  in every session-start briefing. Matched on exact title **and** creation
  window **and** zero activity rows, so a real task that happens to share a
  title survives.
- **3,574 auto-generated "Work in …" threads** closed, not deleted (115). One
  per worktree checkout; 4,059 of 4,061 were still `exploring` and 2 were ever
  promoted. The generator itself is fixed in this same release — see 121.
- **Three named stale DB backups** removed, ~238 MB (113), each safety-copied
  first.
- **Qren-readiness inventory** written to `~/.aos/data/qren-readiness.json`
  (116): machine identity, install shape, detected agent CLIs, every service and
  whether it is disabled, module tiers and database sizes — recorded now, while
  the system still knows itself, so whatever the Qren installer turns out to be
  does not have to discover it from a half-migrated tree. Read-only about the
  system: it inspects and records and decides nothing.

### The desktop app is retired (118)

`apps/desktop/` and `core/bin/cli/release-app` are deleted from the framework,
along with the app half of `/ship` and of `docs/release-channels.md`. Migration
118 removes the two per-machine remnants — `/Applications/AOS.app` and
`~/Library/Caches/am.hish.aos` — and only when the bundle's `Info.plist`
actually identifies it as `am.hish.aos`, because a differently-owned
`/Applications/AOS.app` is somebody else's application. macOS-only; a no-op
everywhere else. The source lives on in git history and in
`~/project/_archive/aos-app`.

### The project layer (119)

`~/project/` stops being a directory nobody is accountable for. Four commands —
`project new|adopt|list|archive` — create, adopt, list and finish a project; a
`.aos/project.yaml` manifest lets each directory say what it is; the zones
`_ref/`, `_archive/` and `_scratch/` make location a statement rather than
metadata about one; and a `project_layer` reconcile check reports anything that
cannot identify itself. Migration 119 installs the zones, `~/project/CLAUDE.md`,
the global `project-structure` rule and `project` on PATH. It moves, renames,
git-inits, adopts and archives **nothing** — migrating the existing directories
is an operator-supervised `adopt` session, and automating it would mean guessing,
which is what produced the mess.

### Dead MCP entries and orphans (120)

The `memory`, `crawler` and `xcode` entries — all three fail to connect at every
session start — are dropped from `~/.claude.json`'s global `mcpServers`, with a
timestamped backup first and per-project blocks untouched; `aos sync-mcp` stops
re-registering `crawler` in the same commit so the next sync does not undo it.
The orphaned `~/.aos/services/slack-lite` is archived (moved, not deleted) to
`~/.aos/backups/retired-services/`. Stale integration status in
`integrations.yaml` is corrected where it was demonstrably wrong (`telegram` was
marked `failed` while `com.aos.bridge` was verified running) and left alone where
the failure is real (`obsidian`'s own `setup.sh --check` still fails).

**120's launcher check found nothing to retire.** The brief named four
LaunchAgents as stalled and crash-looping: `com.aos.scheduler`,
`com.aos.domain-watch`, `com.aos.domain-catch`, `am.hish.superwhisper-launcher`.
Each was checked against its own log and `launchctl` state on the reference
machine before any code was written, per the brief's own instruction to verify
first. All four were alive and doing real work — the scheduler ticking every 5
minutes with 38 jobs defined, domain-watch and domain-catch actively tracking
`quran.garden` and `alhuda.com` with clean logs, and the superwhisper launcher
correctly no-op'ing at its last login. All four show PID `-` and last exit `0` in
`launchctl list` at any given instant, which is what an interval-triggered agent
looks like *between* runs, not evidence of a crash loop. None were retired; the
migration ships with an explicit empty retirement list for that part.

### The "Work in …" thread generator is fixed (121)

`find_thread_by_cwd` (`core/engine/work/backend.py`) was a permanent
`return None` — "the DB has no cwd column" — so the SessionEnd hook's
find-or-create was always create. `~/aos` is a release symlink whose target
directory name changes on every update, so every session in it (or `~/nuchay`,
`~/chief-ios-app`, or any subdirectory) minted a fresh thread at every
SessionEnd: the live DB held 4,635 such rows across only 23 distinct titles, all
`status='exploring'`, growing at up to ~90/day by early September. Migration 121
restores `threads.cwd` (the adapter also self-heals it at construction time) so a
directory gets at most one open thread, ever. The same commit fixes
`link_session_to_thread` writing to a `sessions` table work.db does not have — a
crash the dead `find_thread_by_cwd` had been hiding since it never reached the
"thread already exists" branch. 115 mops up the existing rows; this stops them
being made.

### The fleet registry is retired (122)

`aos fleet status|verify|update` and `core/bin/cli/fleet` (305 lines) are gone.
The command SSH-probed a node registry for "what version are you on" — three of
those nodes have no install to report, and the fourth is another operator's
machine listed `auto_update: true`, so `aos fleet update all` would have run
`check-update --apply` on it over SSH. Migration 122 retires
`~/.aos/config/fleet.yaml` to `~/.aos/backups/retired-config/`, moved and
timestamped rather than deleted, because a config file whose only reader has been
deleted is worse than no file: the next operator reads `nodes:` and believes this
machine still verifies others after every ship. One literal filename, never a
glob over `~/.aos/config`.

Updating is each machine's own business. `catch_up: true` is also removed from
the `auto-update` and `harness-update` crons — its only recorded justification
was a laptop that slept through the 04:00 window, and that laptop has no AOS
install. `/ship` Step 6's remote post-flight is gone for the same reason; the
instinct is kept where it still bites, as Step 4 "Apply to the Runtime", ending
on `aos self-test` and `aos hygiene`, because a push is not a ship.

### Added while the release was open (123–131)

One DB (123: `sessions`/`session_tasks` leave `qareen.db`); the bridge owns its
conversation store (124); QMD collections backfilled on every install (125);
reconcile findings land once in the work inbox (126); comms-intelligence crons
parked (127, 131); work-runner fully decommissioned (128); the last cwd-keyed
threads closed (129); trust-log written automatically on every catalog
dispatch (130). Details per number in the CHANGELOG and the index below.

## Who runs AOS, and how each machine gets this

**Probed by SSH 2026-09-13**, because the rollout order this doc used to carry
named four machines of ours and three of them do not have an install.

| Node | AOS install | How it gets 0.7.7 |
|---|---|---|
| `agents-mac-mini` (this Mini) | **yes** — ours | Dev and release machine. Updates itself: `check-update` every 2h notices, `auto-update` applies at 04:00, or the operator runs `check-update --apply` by hand. At migration level 107, so 108–122 land in one update. |
| `faisal-mini` / `agents-mac-mini-2` | **yes** — another operator's | A live, independent install: v0.7.6, migration level 107, its own agents layered on, Qareen still running there (nobody used it; 108 retires it there too). **On the `stable` channel since 2026-09-13** (it was on `edge`, which would have applied `main` within two hours, unwatched). It takes 0.7.7 only when the `stable` tag is promoted — see the lanes below. |
| `pi5` | no | No `~/aos`, no `~/.aos`. Nothing to update. |
| `mbp` | no | `~/.aos/config` only — no framework tree, 0 LaunchAgents. An instance layer with nothing under it. |
| `imac` | no | A partial `~/aos/core` with no version-control history and no `~/.aos` at all. Not an install; a half-finished copy under another local account's home. |

So two machines run AOS, and they belong to two different operators. Both get the
release; neither is updated *by* the other. The fleet registry and
`aos fleet update all` were the one path that crossed that line, and 122 retires
them — what replaced the guard is simply the absence of a remote trigger.

The old rollout order's steps 2–4 — pi5, then imac, then mbp — were scheduling
work on machines that cannot receive it. In particular, the plan to "confirm
`task_runs` is empty on a second machine" before the work-runner disable ships
further has no second machine of ours to confirm on: that evidence is this
Mini's DB, and it is the only DB there is.

### The two lanes

1. `main` is pushed → this Mini takes it on `edge` (`check-update` within 2h, or `aos update` now).
2. Verify here: migrations 108→131 in `~/.aos/logs/migrations.yaml`, `aos self-test`, `aos hygiene`, the first reconcile pass, the bridge alive, the briefing rendering — and diff what happened against the pre-release dry-run.
3. Anything the real install teaches → 0.7.8 on `main`.
4. `aos promote` (2-day soak, or `--force`) moves the `stable` tag → faisal-mini takes it on its next cycle, watched: snapshot his `~/.aos/config` and both DBs first; then his migration log, self-test, reconcile; then a side-by-side of what differed on a second operator's machine.
5. Whatever his install teaches → 0.7.9.

**Do not rebuild a rollout across pi5, mbp and imac.** If one of them ever gets
an install, the thing to write is a fresh registry, not a restoration of this
one — it was built for machines that had already stopped being installs by the
time the release was cut.

## What to verify after install

### On this Mini

Run these in order and stop at the first failure. Each one is cheap, and a
half-applied release is what this list exists to catch.

1. **`aos self-test`** and **`aos hygiene`** — both clean. These are the two
   commands the ship flow itself now ends on.
2. **Migration level is 122.** `aos migrate --status`. If it stopped short, the
   failing migration's own output says where, and
   `~/.aos/data/update-state.json` records it under `last_apply`.
3. **`check-update` still offers updates.** It runs every 2h; on the next cycle
   the log must read `Up to date` or `Update available on '<channel>'` — never
   `Frozen` or `Out of scope`. Those states no longer exist; if either string
   appears, the machine is running older code than it thinks.
4. **`work-runner` is off and stays off**, and **the services the operator opted
   into are still running** — the bridge especially. 112's `default_off_services`
   reconcile check and the `SentinelPlistDriftCheck` fix are the code most likely
   to switch something off that should be on.
5. **No "Work in …" thread is created twice.** Open and close a session in
   `~/aos`, then again, and confirm one row for that project rather than two —
   `work threads` was retired in this release, so read it off `threads` in
   `work.db` (or `work active`). This is the 121 fix, now keyed on the project
   rather than the cwd string, and it is the one that was silently growing the
   DB.
6. **`~/project/` still looks right.** `project list` should report the zones and
   name whatever has drifted. 119 creates nothing outside `~/project/` and moves
   nothing inside it; if a directory vanished, something else did it.

### On faisal-mini

Watched, not fire-and-forget (the operator's decision 2026-09-13). Before the
`stable` promotion: copy `~/.aos/config/`, `work.db` and `qareen.db` aside.
After his cycle picks it up: migration level **131** in his
`~/.aos/logs/migrations.yaml` with no `error`/`failed` rows; `aos self-test`
and `aos hygiene`; the first reconcile pass. Things that differ from this Mini
and are worth a look there: 108 boots out a Qareen that was actually running;
111/112 do real work if `work-runner`, `sentinel` or `converse` are loaded;
125 adds the curated QMD collections next to his single `vault` one; 129
closes 9,878 cwd-keyed threads; `listen` stays off (his opt-out). Record what
differed — that is the input to 0.7.9.

Nothing. There is no install to verify.

## Things found while building this, worth knowing

1. **`SentinelPlistDriftCheck` ignored the operator's opt-out.** It never
   declared `service = "sentinel"`, so reconcile could not know which service it
   owned and called `fix()` — which re-renders the plist and restarts the
   service — for an operator who had switched Sentinel off. Fixed here, along
   with the same gap in `BridgePollLivenessCheck`. This mattered more than it
   looks: it was the exact path that would have re-armed the arm 112 switches
   off.
2. **`default_off.py` resolved `Path.home()` at import time**, so the first
   caller to import it decided, process-wide, whose `services.yaml` everyone
   else wrote to — in a test run, the operator's real machine. Now resolved per
   call, with a test asserting the live instance is untouched after the suite.
   That test had a second bug of its own: it checked for the *substring*
   `enabled:`, which `default_off.py`'s own header comment contains, so it would
   have started failing on this Mini the moment 111 ran for real. It now parses
   the YAML and asserts no `enabled` key.
3. **The Telegram handler created junk tasks.** Every trigger prefix required a
   trailing space, so a bare `add task:` matched none of them and created a task
   titled "add task:" — the same shape that put `--help` in the task table twice.
4. **The plan's 30-day thread window closes 15 rows of 4,057.** The noise is
   generated continuously and is nearly all recent. Changed to 7 days (3,574
   rows), which still leaves the current working week open.
5. **The update path had two gates that decided whether to update at all**, both
   added for a freeze that is no longer happening: a `frozen: true` policy file
   and a hostname exclusion list. Both are removed on this branch. Nothing in
   AOS now compares version components — "newer commit on your channel" is the
   whole rule. The pause knob an operator actually has is the service opt-out:
   `scheduler` in the `disabled:` list of `~/.aos/config/services.yaml` stops
   the scheduler and with it both `check-update` and the 04:00 `auto-update`.
   `enabled: false` per job exists in `config/crons.yaml`, but that file is in
   the framework tree and an update rewrites it, so it is a shipped decision
   rather than a per-machine one — worth knowing before pointing anyone at it.

## Deliberately not done

- **No n8n migration.** The plan called for one, but migration `109` deletes
  `~/.aos/services/n8n` entirely. A second migration deleting a directory the
  previous one removed is dead code.
- ~~**The generation of "Work in …" threads is unchanged.**~~ **Reversed
  (aos#223, migration 121), same release.** `find_thread_by_cwd` was a permanent
  `return None`; the live DB grew from 4,059 to 4,635 of these rows in three
  weeks with no ceiling in sight, which is a bug, not a recorded behaviour worth
  keeping.
- **`sana-watch`, `ios-deploy`, `qareen-deploy` untouched.** Instance-only on
  this Mini, no plist template, no migration ships them. Marked
  `status_note: instance-only, not installable` in `modules.yaml`; not
  instrumented, per the plan.
- **Nothing applied to any live machine.** No push, no merge, no migration run
  outside `/tmp`.
