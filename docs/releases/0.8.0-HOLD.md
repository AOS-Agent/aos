# v0.8.0 — clean and freeze

**Status: HOLD. Do not ship.** Release only when the Qren installer path is
clear. Everything below is built, tested and dry-run; nothing has been applied
to any machine, and the branch has not been pushed or merged.

Branch: `release/0.8.0` · Base: `main` @ `17453bd` · VERSION: `v0.8.0`

---

## What this release does

AOS stops being a system under development. This is the last feature release:
it sheds what was never used, switches off what should not have been on by
default, and changes the update path so the fleet keeps taking patches and
nothing else. What comes after is Qren, installed deliberately — not an update
that arrives at 4am.

Three things happen at once, and they are separable if any one of them turns
out to be wrong.

### 1. Four services become opt-in

| Service | Why | Reversal |
|---|---|---|
| `work-runner` | `task_runs` held **zero rows on every machine audited** — 905 lines and a resident KeepAlive'd LaunchAgent that never once delegated a task | `work runner enable` |
| `sentinel` | Reads iMessage, drafts follow-through. Autonomous comms defers to Qren | list under `enabled:`, reload plist |
| `converse` | Live multi-turn sessions. Same | same |
| `envoy` | Runs delegated outbound conversations with third parties. Same | same |

The mechanism is a new `enabled:` list in `~/.aos/config/services.yaml`
alongside the `disabled:` list reconcile already reads. **`enabled:` wins and is
never auto-disabled** — by a migration, by reconcile, by anything. Without that
asymmetry, "off by default" and "off by decree" are the same code path, and an
operator who wants Sentinel gets it switched off under them on every update.

`modules.yaml` had `work-runner` as `tier: core` while the service registry
called it `optional` — the precise drift the registry exists to prevent. Aligned.

### 2. The instance gets cleaned

- **368 test-fixture tasks** deleted from `work.db`. The test suite wrote to the
  real database for ~3.5 months; these are the six literal titles from
  `tests/test_engine.py`, 17% of the task table and the bulk of the `t#` bucket
  in every session-start briefing. Matched on exact title **and** creation
  window **and** zero activity rows, so a real task that happens to share a
  title survives.
- **3,574 auto-generated "Work in …" threads** closed (not deleted). One per
  worktree checkout; 4,059 of 4,061 were still `exploring` and 2 were ever
  promoted. The generation code is deliberately untouched.
- **Three named stale DB backups** removed (~238 MB), each safety-copied first.
- **Qren-readiness inventory** written to `~/.aos/data/qren-readiness.json`.

### 3. Updates freeze

`frozen: true` in `~/.aos/config/update-policy.yaml` means `check-update` offers
patches only. "Patch" is decided from the VERSION numbers — same `major.minor`,
higher `patch` — not from trust in the sender. A frozen machine that cannot read
the candidate's version is offered **nothing**: this gate fails closed, unlike
the services opt-out which fails open, because failing open here pushes an
unidentified release onto a machine that asked to stop receiving them.

One Telegram notice goes out, once, ever (migration 117), in plain English:
AOS is finished, Qren is coming, invite only.

A **host scope guard** stops the update path on the excluded mini before any
pull, release build, or service restart — logged, exit 0, because being out of
scope is a correct outcome and a non-zero exit would report a cron failure every
two hours forever.

## Things found while building this, worth knowing

1. **`SentinelPlistDriftCheck` ignored the operator's opt-out.** It never
   declared `service = "sentinel"`, so reconcile could not know which service it
   owned and called `fix()` — which re-renders the plist and restarts the
   service — for an operator who had switched Sentinel off. Fixed here, along
   with the same gap in `BridgePollLivenessCheck`. This mattered more than it
   looks: it was the exact path that would have re-armed the arm this release
   switches off.
2. **The freeze flag nearly destroyed a working config.** `channel-update.yaml`
   was the obvious filename and has been in use since March holding the hourly
   Telegram status settings. The flag moved to `update-policy.yaml`; the old
   file is now read-only, for an operator who set `frozen:` there by hand.
3. **`default_off.py` resolved `Path.home()` at import time**, so the first
   caller to import it decided, process-wide, whose `services.yaml` everyone
   else wrote to — in a test run, the operator's real machine. Now resolved per
   call, with a test asserting the live instance is untouched after the suite.
4. **The Telegram handler created junk tasks.** Every trigger prefix required a
   trailing space, so a bare `add task:` matched none of them and created a task
   titled "add task:" — the same shape that put `--help` in the task table twice.
5. **The plan's 30-day thread window closes 15 rows of 4,057.** The noise is
   generated continuously and is nearly all recent. Changed to 7 days (3,574
   rows), which still leaves the current working week open.

## Deliberately not done

- **No n8n migration.** The plan called for one, but migration `109` (already on
  `main`, not yet applied here) deletes `~/.aos/services/n8n` entirely. A second
  migration deleting a directory the previous one removed is dead code.
- **The generation of "Work in …" threads is unchanged.** Fixing it is a
  behaviour change, and this is a freeze.
- **`sana-watch`, `ios-deploy`, `qareen-deploy` untouched.** Instance-only on
  this Mini, no plist template, no migration ships them. Marked
  `status_note: instance-only, not installable` in `modules.yaml`; not
  instrumented, per the plan.
- **Nothing applied to any live machine.** No push, no merge, no migration run
  outside `/tmp`.

### 120's launcher check found nothing to retire

The brief for 120 named four LaunchAgents as stalled and crash-looping:
`com.aos.scheduler`, `com.aos.domain-watch`, `com.aos.domain-catch`,
`am.hish.superwhisper-launcher`. Each was checked against its own log and
`launchctl` state on the reference machine before any code was written, per
the brief's own instruction to verify first. All four were alive and doing
real work — the scheduler was ticking every 5 minutes with 38 jobs defined,
domain-watch and domain-catch were actively tracking `quran.garden` and
`alhuda.com` with clean logs and no errors, and the superwhisper launcher had
correctly no-op'd or launched the app at its last login. None were retired;
migration 120 ships with an explicit empty retirement list for part (a) and
does (b) service-dir orphans, (c) dead MCP entries, and (d) integration status
drift instead. See the migration's own docstring for the full verification
detail.
